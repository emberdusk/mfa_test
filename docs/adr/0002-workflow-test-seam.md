# 工作流以工厂暴露纯逻辑缝，并据此引入首个测试项目

步骤 5 的工作流示例（大写 → 反转）是一条纯文本处理工作流，与模型后端无关。为让「输入 → 输出」可以被自动断言，我们把构图逻辑从顶层语句里抽到一个对外的工厂（返回已连边、已声明输出的工作流），程序入口只负责「取工作流 → 运行 → 打印事件」；并据此新增本仓库的首个测试项目，对工作流做一条离线的端到端断言。

背景：在此之前，伞形 spec 约定每一步能力都以端到端 `dotnet run` 验证，不引入测试项目或测试缝。工作流是第一个**纯逻辑、无外部依赖**的能力——人工肉眼的验证收益低、回归性差，因此自本步起就地放宽该约束（而非全仓库强制）。

## 考虑过的替代方案

- **入口内的 `internal` 构图方法 + `InternalsVisibleTo`**：把装配留在入口里，靠可见性技巧让测试够得着，耦合更重。
- **测试内复制一份构图**：重复实现，实现变了测试却不会失败，是最差的缝。
- **维持原状不引入测试**：工作流是天然可测点，放弃自动化的收益不划算。

最终采用**工厂缝**：它与仓库既有的「入口只编排 / 工厂做装配」约定同构（对照 `AgentFactory`），并落在本能力可用的最高一点。

## 后果

- 仓库自本步起有了 `tests/` 目录与首个测试项目；伞形 spec 的 Testing Decisions 已相应更新并指向本决策。
- 后续「纯逻辑能力」沿用同一缝型：工厂返回可运行对象，测试只断言其外部行为。
- agent 类步骤（1–4、6–7）仍以端到端运行为准；本次是就地放宽，不是对全仓库的强制要求。
- 与 [ADR-0001](0001-use-opencode-go-via-openai-compatible-chat-completions.md) 的关系：ADR-0001 结尾称本仓库示例「是无单元测试缝的顶层语句控制台程序」。该表述自本决策起不再对全仓库成立——工作流项目引入了首个测试缝；ADR-0001 关于 OpenCode Go 后端的其余内容不受影响。
