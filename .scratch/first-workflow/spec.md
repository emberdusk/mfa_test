# Spec: 首个工作流（Executor + Edge，含测试缝）

**Status:** ready-for-agent
**对应工单:** `.scratch/agent-framework-get-started/issues/05-first-workflow.md`
**相关:** `.scratch/agent-framework-get-started/spec.md`（伞形/里程碑 spec）、[ADR-0002](../../docs/adr/0002-workflow-test-seam.md)（本 spec 要求的决策记录，已随实现落盘）
**来源:** 一次 `/grill-with-docs` 盘问（两轮前沿问题全部按推荐定案）

## Problem Statement

跟随 Microsoft Agent Framework 入门教程的开发者，在仓库里目前只能看到 **agent 类**能力（步骤 1–4：单轮 / 工具 / 多轮 / 记忆），看不到教程步骤 5 讲的**图式编排**——把多个步骤（执行器）用边连起来、逐级传递数据的模型。而且这四个步骤的验证全靠人工 `dotnet run` 观察输出，仓库**没有任何自动化验证缝隙**，工作流这种「纯逻辑、输入到输出」的能力却拿不到一条稳定断言。

因此需要一个**不依赖模型、不联网即可运行**的工作流示例，把「执行器 → 边 → 运行 → 事件」这条主线演示清楚；同时为「输入→输出」建立仓库的第一个测试缝，让这类纯逻辑能力可以被自动验证。

本 spec **不**关心模型后端：工作流是纯文本处理，与 OpenCode Go、`AgentFactory`、`LLM_API_KEY` 全都无关。

## Solution

新增一个**独立的工作流项目**：两个执行器由一条边顺序连接——第一个把文本转大写，第二个把文本反转；用 `WorkflowBuilder` 构图、`InProcessExecution` 运行，遍历运行产生的事件并打印每个执行器的完成事件。输入 `"Hello, World!"`，最终输出 `"!DLROW ,OLLEH"`。

为让「输入→输出」可自动断言，构图逻辑从程序入口抽出为一个**工厂缝**（对外暴露「构建好的 Workflow」），程序入口只负责「取工作流 → 运行 → 打印事件」；并据此新增仓库**第一个测试项目**，对工作流做一条端到端断言。该测试缝决策由一篇新 ADR 记录。

最后同步文档：README 增加本步运行与测试方式；根目录新增术语表，收录本步引入的领域词汇；修正工单编号笔误并把工单收尾。

## User Stories

1. 作为跟随教程的开发者，我想要把「大写」和「反转」两个执行器串成一条数据流，这样我能理解工作流的顺序编排。
2. 作为跟随教程的开发者，我想要运行工作流并看到**每个执行器各自的完成事件**（执行器 ID + 其结果），这样我能理解事件是如何随数据流动产生的。
3. 作为跟随教程的开发者，我想要看到最终输出是 `"!DLROW ,OLLEH"`，这样我能确认整条工作流按预期串起来了。
4. 作为跟随教程的开发者，我想要一个执行器用**函数绑定**（`BindAsExecutor`）产生、另一个用**执行器子类**实现，这样我能对照学到两种定义执行器的方式。
5. 作为学习者，我想要该项目**不需要 API Key、不需要网络**即可运行，这样我在没有后端时也能学习和验证工作流。
6. 作为学习者，我想要该项目**不引用** agent 代码、不经过 `AgentFactory`，这样工作流与模型后端解耦，概念隔离清晰。
7. 作为学习者，我想要每个能力都能单独 `dotnet run` 演示，这样我学习本步时不被其它步骤干扰。
8. 作为维护者，我想要构图逻辑集中在一个**工厂**里（对齐仓库既有的装配入口风格），这样程序入口只管编排、构图只管装配，职责不混。
9. 作为维护者，我想要**首个测试项目**对工作流做「输入→输出」的端到端断言，这样这类纯逻辑能力不再只能靠人工肉眼验证。
10. 作为维护者，我想要测试**只断言外部行为**（运行的输出/事件），不断言执行器内部实现，这样实现微调不会打碎测试。
11. 作为维护者，我想要测试**离线可跑**、不依赖密钥或网络，这样它能在任意环境（含 CI）稳定通过。
12. 作为维护者，我想要测试缝落在**最高的那一点**（整个已构图的工作流），这样全仓库新增的测试缝数量保持最少。
13. 作为维护者，我想要该决策被一篇 **ADR** 记录（为什么这个原本无测试的仓库现在有了首个测试项目与工厂缝），这样未来读者不会困惑「为什么这里突然有测试」。
14. 作为维护者，我想要工作流项目被解决方案 `MfaTest.slnx` **收录**，测试项目亦然，这样 IDE / `dotnet build` 能覆盖到全部项目。
15. 作为维护者，我想要 **README** 记录本步的运行与测试方式、并把项目纳入结构树，这样我能按需回看。
16. 作为维护者，我想要根目录出现一份**术语表**，用统一词汇（Executor、Edge、Workflow、Run、WorkflowEvent）指称这些概念，这样后续步骤（工具包、托管）的对话不歧义。
17. 作为维护者，我想要工作流的**输入/输出契约**与官方示例保持一致（`"Hello, World!" → "!DLROW ,OLLEH"`），这样本项目仍是可对照的教程镜像。
18. 作为维护者，我想要工单里明显的**编号笔误**（标题写成「# 02」而文件名是 05）被修正，这样跟踪器编号自洽。
19. 作为维护者，我想要工单在本步完成后置为 `done` 并附一条实现记录，这样推进轨迹可回看。
20. 作为维护者，我想要伞形 spec 中「暂不引入测试缝」的旧决策被**明确指向**新决策而非悄悄覆盖，这样阅读 spec 的人不会被误导。
21. 作为维护者，我想要实现与文档一次性原子提交，提交信息沿用既有风格，这样历史与步骤 1–4 保持一致。

## Implementation Decisions

**项目与依赖**
- 复用已存在但只有残留 `bin/obj` 与空 `Executors` 目录的工作流项目目录（清掉残留），补上项目文件与入口源码。
- 工作流项目**完全独立**：不引用 agent 项目、不经过 agent 装配、不需要密钥、不联网。
- 引用工作流包，版本**固定**为与仓库既有包一致的 `1.24.0`。
- 目标框架与仓库一致（`net10.0`，Exe）。

**构图与执行**
- 工作流由 `WorkflowBuilder` 从第一个执行器出发，加一条边连到第二个执行器，并声明第二个执行器的输出为工作流输出；经 `InProcessExecution` 运行。
- 第一个执行器为**函数绑定**式（把 `string→string` 的大写函数绑定为执行器）；第二个执行器为**执行器子类**，覆写处理方法返回反转后的字符串。两者定义方式并列，贴合官方 C# 示例的语义。
- 输入固定为 `"Hello, World!"`；预期最终输出 `"!DLROW ,OLLEH"`。
- 运行后**只**遍历运行事件、打印两个执行器的完成事件（`执行器ID: 数据`），不额外打印「最终输出」——因为反转执行器已是输出执行器，它的完成事件数据即最终结果。

**测试缝**
- 从程序入口抽出工厂 `WorkflowFactory`，对外暴露「构建好的工作流」（`Build()`），程序入口改为「取工作流 → 运行 → 打印事件」。理由：对齐仓库既有的「入口编排 / 工厂装配」约定，并提供一个对外可测的**唯一、最高**缝。
- 新增仓库首个测试项目，对工厂返回的工作流做**一条端到端测试**：运行后断言输出等于 `"!DLROW ,OLLEH"`。
- 测试框架沿用 SDK `dotnet new xunit` 模板默认（xunit 2.x 系 + Test.Sdk + runner；不额外加 `coverlet.collector`），目标框架 `net10.0`。
- 测试项目放在新建的顶层 `tests/` 目录（`src/` 留给可发布产物），并被 `MfaTest.slnx` 收录。

**决策记录**
- 新增**一篇** ADR-0002，主题聚焦「工作流以工厂暴露纯逻辑缝，并据此引入仓库首个测试项目（离线、不接模型）」；把「工作流项目独立于 agent 后端」作为背景写进其 Context。理由：真正满足「难逆 + 需背景 + 有取舍」三条件的是测试缝（它推翻了伞形 spec 原有的「暂不引入测试缝」），而「项目独立」是早已定案的能力叠加。

**文档与跟踪器**
- README：运行区补工作流项目的 `dotnet run` 与预期输出；补一行 `dotnet test`；结构树加入工作流项目与测试项目；正文新增「工作流」小节，串讲 Executor / Edge / 运行 / 事件。
- 新增根目录术语表（`CONTEXT.md`，纯词汇表、不含实现细节），收录：Executor、Edge、Workflow、Run、WorkflowEvent（含完成事件）。
- 修正工单标题的编号笔误，使文件名与标题编号一致。
- 工单完成后置 `Status: done` 并在 `## Comments` 追加一条实现记录。
- 伞形 spec 的 Testing Decisions 段更新为：自本步起引入首个测试项目与测试缝（指针指向本 spec 与 ADR-0002）。

## Testing Decisions

- **好测试的标准**：只断言**外部可观察行为**（运行工作流后得到的输出/事件），不断言执行器内部实现。理由：执行器内部实现会演进，断言它会让测试变脆；spec 一贯只测外部行为。
- **测什么**：工作流端到端——用工厂构建的工作流跑 `"Hello, World!"`，断言输出 `"!DLROW ,OLLEH"`。仅此一条。
- **缝**：唯一新缝为 `WorkflowFactory`（返回已构图的工作流），它是本能力可用的**最高**一点，避免为两个执行器各开一个更低的缝。**（已与用户确认。**）
- **测哪些模块**：工作流项目（经工厂缝），不测 agent 项目。
- **先例（prior art）**：仓库此前**没有**测试项目——本步是首个。因此本测试同时充当后续「纯逻辑能力」测试的样板：离线、单缝、端到端。

## Out of Scope

- agent 类能力与模型后端（步骤 1–4、6、7）；本步与 OpenCode Go、密钥、网络完全无关。
- 更复杂的工作流拓扑：分支、并行、多路输入、条件边、循环。
- 工作流的检查点 / 暂停恢复 / 持久化。
- 对执行器内部实现的单元测试。
- 引入 CI 管道或测试覆盖率门禁。
- 修改工作流的输入/输出以外的官方示例语义（保持教程镜像）。

## Further Notes

- **与伞形 spec 的关系**：本 spec 是对 `.scratch/agent-framework-get-started/spec.md` 中「步骤 5」的细化与**局部覆盖**——特别是其 Testing Decisions 里「暂不引入测试项目或新测试缝」这一条，自本步起不再成立。已在伞形 spec 中留下指针，避免两处决策互相矛盾。
- **可离线验证**：与 spec 的 Further Notes 一致，工作流步骤（5）是不接后端也能端到端验证的一步；本步还额外提供了自动断言。
- **术语**：本步引入的 Executor / Edge / Workflow / Run / WorkflowEvent 将被写入新建的 `CONTEXT.md`；后续步骤（6 工具包、7 托管）沿用同一套词汇。
- **编号**：工单文件名 `05-first-workflow.md` 与教程目录顺序一致；其标题的编号笔误在本步一并修正。
- **未被采纳的选项**：测试缝的其它落点（入口内的 `internal` 方法 + `InternalsVisibleTo`、或测试内复制构图）已被排除——前者靠可见性技巧、后者重复实现；工厂缝与仓库既有装配约定同构，故采用。
